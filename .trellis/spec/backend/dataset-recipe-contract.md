# Random Style-Dataset Recipes

## Scope / Trigger

Use when changing recipe storage, the recipe engine, the basic template, recipe item
fields on dataset runs, the recipe editor or the review draw filter. Recipe items are
ordinary dataset-run items and inherit [Dataset Runs](./dataset-run-contract.md).
The fixed 322-item style library was retired with this feature (2026-11-12).

## Signatures

- Schema 14 `dataset_recipes(user_id, id, name, recipe_json ≤1 MiB, created_at, updated_at ms)`.
- `GET /api/dataset-recipes` → `[{id, name, updated_at}]`; `GET|PUT|DELETE /api/dataset-recipes/{uuid}`.
  PUT `{name, recipe, expected_updated_at?}` upserts; stale/unknown expected → 409
  `recipe_conflict`; >100 per owner → 409 `recipe_limit`.
- `POST /api/dataset-recipes/sample {recipe, n 1..4000 (`MAX_ITEMS`), seed uint32}` → `{items, stats}`;
  pure, offline, nothing stored. `GET /api/dataset-recipes/templates/basic`.
- Recipe validation errors on these routes return 422 `recipe_invalid` with
  `"<json path>: <message>"`; every other route keeps the generic validation body.
- `DatasetItem` gains optional `draws[]` (≤128 `{partition, option, label, values?, reason?}`),
  `style_edits {add[], remove[]}` (≤32 additions, ≤128 removals, ≤300 characters per
  normalized tag) and `recipe {id, name}`; all are
  excluded when empty so legacy items stay byte-identical.

## Contracts

- Engine: `recipe_engine.py` (pure). Draw in `draw_order`; structural effects (hide,
  set, consume, remove_partitions/options, allow_options/values) apply immediately and
  withdraw already drawn targets (refund resources, no redraw, `stale_dependency` when a
  later draw depended on it). Rules run after all partitions. Tag effects apply at
  assembly in `prompt_order`. A partition whose only eligible option is `none` is a
  `conflict` skip (none effects do not apply). Prompts > 1000 chars are reported, never
  truncated. Same recipe + n + seed ⇒ identical result.
- Draw-time conditions may only reference earlier partitions/state; rules may reference
  anything. Child options must set `age=child`; with child options present, unsafe
  content needs an explicit `not state age=child` guard.
- `dataset_parameters()` resolves the item style as pool style for the ordinal, then
  `resolve_style(style, style_edits)` (weight-syntax aware removal, append, `//` lines
  untouched). Creation rejects any pool style that resolves blank; character runs reject
  `style_edits`. Captions still come from `item.prompt` only, so `style_add` tags are
  never captioned.
- Quota partitions draw once and may have visibility/condition requirements. Sampling
  proceeds across the batch in draw order, allocating largest-remainder quotas separately
  for each identical set of eligible options and effective weights. Invisible/conditional
  skips consume no quota; later withdrawals are reported as `quota_misses`. Slot values
  balance repeated draws within the same legal value/weight set. Small-batch remainder
  ties are seed-shuffled. Same recipe, seed and full batch size remain deterministic.
- Tag comparisons remove emphasis and normalize case, underscores and whitespace.
  Region-bound `style_tags` are mandatory final removals from both content and style;
  later rules cannot re-add a detail whose required region is invisible. Keep `closed
  eyes`, bangs, glasses and external eyelashes distinct from visible eyeball details.
- Recipe style edits and queued dataset items share one normalization/validation
  contract. Additions retain numeric and brace/bracket emphasis; comma groups become
  individually balanced tags (`3::a, b::` becomes `3::a::`, `3::b::`). Removal selectors
  normalize to plain tag names. Enforce count and length limits after normalization;
  aggregate edits that exceed the item limits fail sampling with `recipe_invalid`
  before they can become an unusable draft. Never silently strip requested weights.
- Queue preflight checks each item's resolved style against every pool member,
  including the combined content/style length after edits. Style additions stay out
  of the item's content and exported caption. Test the sample-to-queue boundary with
  disposable synthetic data and a fake provider, never runtime logs or real records.
- Publish weighted-style compatibility in the API before its web preflight/input
  changes. Retain that API during any web fallback: frozen items may already contain
  weighted style additions that the previous plain-tag-only model cannot read.
- Ids are immutable; labels are display only. Object ids are generated by the editor
  (`<prefix>-<8 base36>`), the template uses fixed readable ids, the server never
  generates object ids.
- Glosses are display-only (option label → recipe glossary → `TAG_ZH`); batch lookup
  uses `/api/tags/search` sequentially and stops on 429.

## Wrong vs Correct

- Wrong: write `gentle smile` into the item prompt — it becomes caption text.
- Correct: `style_add` it per item so the LoRA absorbs it as style.
- Wrong: reference partitions by name. Correct: by id; renames change nothing.

## Operator default and reset (2026-11-12)

- The default is one adult woman; eight equal hair colors (3x except white/black),
  bundled hairstyles and 6x bangs, 10% dark skin, and one mutually exclusive fantasy
  partition (80% ordinary, 10% long pointed ears, 10% demon horns).
- Pose groups: yoga 43.75%, combat 26.25%, ordinary 12.5%, lying 5%, forward folds 7.5%,
  ground/support 5%. Complex poses require full-body framing and consume their hands.
- Pose bundles specify the named movement, support points, limb positions and torso
  alignment together. Downward dog includes grounded hands/feet, spread palms and an
  extended spine. Yoga also includes child, extended puppy, dolphin, one-legged
  downward dog, cat and cow poses; reverse plank belongs to ground/support. Adding
  variants balances choices inside their group without changing group proportions.
- The subject explicitly includes `adult woman`. Short wavy hair is a separate
  equally allocated hairstyle; only bangs receive 6x emphasis. Rear-quarter directions
  remain the same two quota options, with explicit `rear three-quarter view` wording.
- Positive focus tags use 3x emphasis (`3::face focus::`); removal selectors remain
  plain names and remove weighted forms through canonical matching.
- Body type is 80% large / 10% medium / 10% small breasts among adult items with
  visible upper body; each choice removes contradictory size tags from the baseline
  style, and a hidden upper body removes all bound size tags. Forehead marks are
  90% absent / 10% a coupled forehead mark and
  red markings among items with visible forehead. Covered foreheads and hidden faces
  remove mark details from content and style. Draw marks after head accessories so
  hats cannot invalidate an already assigned quota. Relaxed expressions obey the same
  closed-mouth cleanup as other closed-mouth choices.
- Side profiles remove heterochromia even when a later bangs choice leaves both eyes
  otherwise eligible. Child pose hides the face because its forehead rests on the
  floor. Include forced close-up/back/night combinations when checking the combined
  style-removal bound after extending the template.
- Barefoot is 70% of feet-visible items, with no socks. Clothing families constrain
  bottoms and shoes (school: pleated skirt; Arabian: pelvic curtain/harem pants;
  kimono: geta or barefoot). Head/ears/horns are separate from face visibility.
- Default cleanup uses explicit exact tag aliases, including the default palette's
  colored shoes/socks. Skin, hair and fantasy choices also remove contradictory
  baseline style tags. Region bindings and each style-removal effect allow 128 tags;
  generated items allow 128 removals and 32 additions. Validate the combined default
  removals across different seeds when extending the vocabulary.
- Browser previews sample the configured full N and show its first 20 items. Append
  and replace reuse that result; recipe, identity, N, seed or dialog-state changes
  invalidate it and cancel/ignore stale responses. Weighted tags retain Chinese glosses.
- `novelai-admin clear-dataset-recipes --all-users` explicitly deletes only saved
  recipe rows in one transaction and prints `{"deleted_recipes": N}`. It never loads
  recipe values, removes runs/jobs/images, or runs as a migration/startup hook. Existing
  runs keep frozen items; a fresh editor without saved recipes opens the new template.
- Verification uses invented recipes and disposable databases only. Never inspect
  real prompts, captions, dataset images or database payloads to validate a reset.

## Partition import/export (web only, 2026-11-13)

- File `{format: "nai-recipe-partitions", version: 1, partitions[], slots[], regions[],
  resources{}, states{}, glossary{}}` (`apps/web/src/recipe-partitions.ts`). Export
  keeps draw order and bundles only what the partitions use (regions with ancestors).
  Import also accepts a whole recipe file `{name, recipe}` or a bare recipe and lets
  the user pick partitions. No server endpoint: the result is an editor change
  (undoable) validated by the server on save.
- Import touches only the chosen partitions. A partition id that already exists needs
  an explicit choice per partition: `replace` (keeps its position; references
  elsewhere to options the new version drops are removed like `deleteOption`) or `copy`
  (`<id>-2`…, ≤64 chars; references among the imported partitions follow the rename).
  New partitions go to the end of `draw_order`/`prompt_order`.
- Recipe-level definitions are only added, never overwritten. A slot with the same id
  but different values (id/tag/weight) is added as `<id>-2` and the imported
  placeholders, slot settings and `allow_values` keys follow. States are recipe-wide
  and keep their keys.
- References the merged recipe cannot satisfy (partition/option/state/region) are
  removed from the imported partitions and listed before import; a weight modifier
  with a missing reference is dropped whole.
- `findReferences` removing the last condition of a rule deletes the rule (a rule
  needs `when`; an unconditional rule would fire on every item).
